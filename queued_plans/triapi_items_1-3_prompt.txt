Three well-understood, low-risk fixes queued in CARRYOVER.md, all final decisions, do not ask clarifying questions:

1. scripts/dispatcher.py's breakdown_plan() runs its post-breakdown guards (_enforce_file_size_ceiling, _enforce_no_raw_edits_to_encrypted_files, the module-import-order guard, the test-context guard) on EVERY call, including resuming an already-fully-broken-down run -- not just once after the initial breakdown. This means a resume can be retroactively blocked the moment ANY item's target (not just the one currently being resumed/dispatched) trips a guard against its CURRENT on-disk state, even though that item already passed validation in the original breakdown pass. Real incident: AGENTS.md itself (a later, unrelated item's target) grew past the size ceiling between an initial breakdown and a resume, blocking the resume entirely. Fix: these post-breakdown guards should run once, immediately after the initial breakdown completes (i.e. only when state["breakdown"]["phases"] is being freshly assembled from chunks, not when breakdown_plan() is re-entered to resume/continue dispatching an already-populated state["breakdown"]). A resume should trust the prior successful validation pass instead of re-litigating it against unrelated items' current disk state. Investigate breakdown_plan()'s actual resume/re-entry logic first (how does it currently detect "this state already has a breakdown, skip re-chunking" vs "freshly breaking down"?) and gate the guard calls behind that same condition, not a new one. Add a regression test.
