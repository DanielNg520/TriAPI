## Executive Summary & Rationale

TriAPI is an autonomous multi-tier code repair and dispatch system where failed tasks escalate sequentially across tiers (Tier 4 -> Tier 3 -> Tier 2 -> Tier 1 -> Tier 5). Prior to run 20260903-220300-6f7574, individual tiers independently queried historical knowledge bases using ad-hoc keyword matching. This approach suffered from three architectural limitations:

1. **Redundant Spend and Prompt Drift:** Re-querying knowledge bases on every tier escalation introduced non-deterministic prompt drift across retry attempts and multiplied prompt token spend across fallback chains.
2. **Keyword Match Precision Limits:** Pure token-overlap search frequently missed relevant historical lessons and code snippets that used synonymous phrasing or different naming conventions.
3. **Unbounded Prompt Growth Risks:** Without centralized budgeting across knowledge sources, injected snippets risked inflating prompt size and exhausting context windows on local models.

To resolve these limitations without introducing marginal API costs or external cloud dependencies, TriAPI implemented a unified retrieval-augmented generation (RAG) and memory retrieval layer. The subsystem indexes historical post-mortems and reusable snippets into a unified in-memory index, queries them using local vector embeddings generated by Ollama (`nomic-embed-text:latest`) with graceful fallback to keyword search, enforces strict top-K and character caps, and injects retrieved context exactly once at dispatch time.

## Architecture & Design Principles

The design of the RAG/memory layer adheres to four core architectural principles specified in `docs/design_rag_layer.md`:

### 1. Exactly-Once Retrieval Lifecycle

In TriAPI, tasks escalate sequentially upon verification failure. Performing retrieval repeatedly at each tier escalation introduces latency, causes non-deterministic context drift between attempts, and multiplies prompt token spend.

- **Single Fetch Point:** Context retrieval executes exactly once per task during the dispatch preparation phase in `scripts/orchestrator.py` (`orchestrator.run_task()`), immediately before the initial Tier 4 drafting attempt.
- **Context Injection:** The retrieved memory snippets are formatted into a markdown block and combined with task-referenced file contents via `scripts/tier4_worker.py` (`build_context_blob()`).
- **Immutable Escalation Threading:** The resulting unified `context_blob` is passed into `orchestrator.run_task()` and threaded as an immutable argument through all downstream tiers:
    - Tier 4 Worker (`tier4_run`)
    - Tier 3 Debugger (`tier3_escalate`)
    - Tier 2 Manager (`tier2_escalate`)
    - Tier 1 Planner (`tier1_escalate`)
    - Tier 5 Librarian (`librarian_escalate.run`)
- **Deterministic Baseline:** Escalation tiers evaluate against the exact same context baseline without executing secondary retrieval queries.

### 2. Local Embeddings with Graceful Fallback

Semantic retrieval provides significantly better recall for complex bug patterns and architectural directives than simple keyword overlap, but external cloud embedding APIs introduce recurring per-token costs, latency, and content-filter risks.

- **Zero Marginal Cost:** Vector embeddings are generated completely on local hardware using Ollama running `nomic-embed-text:latest`, wrapped by `scripts/embedding_client.py`.
- **Strict 5-Second Timeout:** Local embedding requests enforce a strict 5-second timeout and return typed `None` on any failure (connection error, timeout, or missing model).
- **Graceful Fallback:** If the Ollama daemon is unreachable, times out, or fails, the retrieval layer immediately falls back to deterministic keyword matching:
    - `scripts/hivemind_util.py` (`search_hivemind`) for reusable snippets.
    - `scripts/lessons.py` (`select_relevant`) for past mistake post-mortems.
- Under no circumstances does the system call external paid embedding APIs.

### 3. Strict Context Sizing and Hard Ceilings

To protect local tier context windows (such as Tier 4 context limits governed by `scripts/tier4_context.py`) and prevent reasoning degradation:

- **Top-K Limit:** At most top-K=3 items are selected across all indexed memory sources.
- **Global Character Cap:** A strict hard ceiling of 4,096 characters is enforced across the entire injected memory block, including headers, metadata, and formatting.
- **Enforcement Mechanism:** Candidate items are ranked by cosine similarity (or keyword relevance in fallback mode) and accumulated in descending order. Items exceeding the remaining character budget are truncated or omitted to guarantee the 4,096-character limit is never breached.

### 4. Unified In-Memory Index Bridging Dual On-Disk Schemas

On disk, TriAPI maintains two separate knowledge stores with distinct schemas and editing cadences:

- `knowledge/hivemind.md`: Curated, XML-tagged reusable code snippets and architectural patterns.
- `knowledge/lessons.jsonl`: JSON Lines records capturing post-mortem mistake analyses, root causes, and explicit directives.

Merging these files on disk would disrupt existing tooling, introduce schema churn, and obscure git diffs. Instead:
- **On-Disk Separation:** Both files remain separate and retain their existing formats and editing practices.
- **Runtime Unification:** `scripts/rag_index.py` parses both files at startup into a unified in-memory representation. Embeddings are generated once per run, creating a single vector space where snippets and lessons compete directly for top-K ranking under the shared 4,096-character ceiling.

   - Added `memory_rag` configuration block (`enabled: true`, `embedding_model: nomic-embed-text:latest`).
   - Loaded and validated via `config_loader.py` per TriAPI standard conventions.

5. **`scripts/orchestrator.py`:**
   - Updated `orchestrator.run_task()` to execute `retrieve_context()` exactly once per task.
   - Merges retrieved context into `context_blob` and threads it across all escalation tiers (`tier4_run`, `tier3_escalate`, `tier2_escalate`, `tier1_escalate`, `librarian_escalate.run`).
   - Eliminated independent knowledge base queries from individual tier modules.

6. **`tests/test_rag_pipeline_wiring.py`:**
   - Integration tests verifying exactly-once retrieval threading and asserting that downstream tiers make zero independent retrieval queries.
